Trustworthy Telemetry and Event Design

This recording is an editorial draft adapted from the revised lesson. It has not completed the final dialogue and audio review.

Before we begin

Guide: Today we're talking about Trustworthy Telemetry and Event Design. By the end, you'll know why this matters, how to use it, and what to notice in a real product.

Host: What is the problem we are trying to understand?

Guide: Telemetry is instrumentation that records product and system behaviour for defined decisions. An event name is not evidence until its trigger and semantics are explicit.

Events are claims about state

Host: What changes when we look at events are claims about state?

Guide: Model the domain before naming events. Distinguish:

Guide: intent from attempt; client display from actual exposure; request from server acceptance; pending from completion; failure from cancellation; retry from a new instance; recovery from silent abandonment.

Guide: For each event define actor, entity, state transition, trigger, authoritative source, client or server timestamp, experiment assignment, schema version, required properties, allowed values, identity and join keys, deduplication, privacy classification, owner, and quality tests.

Guide: Client telemetry can show what was rendered and interacted with but may be lost through navigation, blocking, offline use, or device failure. Server telemetry is generally more reliable for processing states but cannot prove what a person saw or understood. Reconcile streams through stable identifiers and clear source authority.

Design an event contract

Host: What changes when we look at design an event contract?

Guide: Begin with the behaviour and causal model, not every clickable element. Instrument states needed to test decisions and diagnose important paths. Clickstream detail without semantic state produces volume without understanding.

Guide: An event contract includes:

Guide: business meaning and non-meaning; exact emission condition and emitting system; entity lifecycle and legal transitions; properties, types, null rules, and units; identity, consent, and cross-device rules; latency and late-arrival expectations; retry/idempotency behaviour; versioning and migration policy; tests, monitors, owner, and downstream consumers.

Guide: When meaning changes, version the event or metric. Do not silently retain a name and rewrite history.

Transfer example: identity verification

Host: What changes when we look at transfer example: identity verification?

Guide: An event called verificationfailed might mean document rejected, camera unavailable, server timeout, user cancelled, or session expired. Combining them produces an alarming but unactionable rate. A state model separates user intent, technical attempt, vendor response, retry, recovery, and final verified outcome while avoiding storage of document content.

Data quality is a live product responsibility

Host: What changes when we look at data quality is a live product responsibility?

Guide: Monitor completeness, duplication, freshness, validity, consistency, and distribution. Compare client and server signals, reconcile source-of-truth totals, and investigate impossible transitions. Broken instrumentation deserves incident priority because teams operating blind can expose people to undetected harm.

Guide: Document known gaps beside dashboards. A data pipeline being available does not mean the measurement is trustworthy.

Where this can go wrong

Host: What changes when we look at where this can go wrong?

Guide: Visible-is-fired: exposure records control availability rather than actual encounter. State compression: attempt and fulfilled outcome share one “complete” label. Client-only truth: lossy interface logs represent server or service outcome. Schema drift: releases change meaning without versioning.

Guide: Identity collision: people, accounts, referrals, sessions, and attempts are joined incorrectly. Overcollection: sensitive content is captured without a justified decision. Dashboard-first instrumentation: charts precede domain semantics and quality tests.

Treat telemetry as a governed product model

Host: What changes when we look at treat telemetry as a governed product model?

Guide: The tracking plan begins with decisions and measures. Every event states which question it supports and what it cannot observe. Page views do not reveal comprehension; button clicks do not prove intention; missing events can mean technical loss or no behaviour.

Guide: Server events are preferred for authoritative service state, while client events can describe interaction if consent and reliability are appropriate.

Guide: Quality controls detect duplicate events, missing properties, impossible sequences, version drift, bot or test traffic, sample-ratio anomalies, and delayed ingestion. Engineers validate against real case histories before release. Data contracts and ownership make breaking changes visible, and historical dashboards record definition shifts.

Guide: Privacy uses minimisation, purpose limitation, access control, retention, and review. Sensitive clinical content is not copied into analytics because it may be useful later. Debugging identifiers are separated and protected. Trustworthy telemetry acknowledges the people it cannot observe and remains paired with direct and operational research.

Transfer example: checkout

Host: What changes when we look at transfer example: checkout?

Guide: purchaseclicked is not a purchase. Authorisation, order creation, inventory reservation, fulfilment, cancellation, and refund have different sources and consequences. A governed event model prevents conversion from being counted before value exists.

The harder decision

Host: Where does the harder design decision appear?

Guide: Instrumentation determines whose behaviour becomes legible and which states disappear. Senior designers help define event semantics because telemetry will later be treated as a description of experience.

Guide: Establish a cross-functional catalogue, review instrumentation in design and code changes, give broken data feature-level priority, and fund deletion and migration—not only collection.

Product example

Host: Can we see that in a concrete product situation?

Guide: Illustrative scenario: a delivery app. An event called “ordercomplete” fires both when payment succeeds and when a confirmation screen loads from cache. The metric cannot support decisions until its meaning is repaired. Specify event names, triggers, identifiers, missing-data checks, and privacy limits so telemetry corresponds to the behaviour the team claims to measure.

Try it yourself

Host: What should I notice the next time I use a product?

Guide: Open an analytics event list if you have access. Select a name such as submitted or active. Can two teams independently infer the same trigger, entity, and outcome? If not, the event is ambiguous evidence.
