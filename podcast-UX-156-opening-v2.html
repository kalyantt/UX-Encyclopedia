Accessibility Quality in a Design System

This recording is an editorial draft adapted from the revised lesson. It has not completed the final dialogue and audio review.

Before we begin

Host: Accessibility Quality in a Design System.

Guide: Accessibility quality in a design system means components encode accessible structure, interaction, content expectations, and states from the start. Tokens support contrast and spacing; component contracts define focus, names, roles, keyboard behaviour, errors, and motion; documentation explains how product teams preserve those qualities in context.

Why it happens

Host: Why does that happen?

Guide: Test components in realistic compositions, not only in isolation. A component can be correct alone and fail in a form, dialog, responsive layout, or custom workflow. Make accessibility requirements part of contribution review, release criteria, and regression checks.

Provide a strong floor without promising automatic compliance

Host: What changes when we look at provide a strong floor without promising automatic compliance?

Guide: A system can encode accessible defaults—semantic structure, focus treatment, keyboard behaviour, contrast roles, target size, motion preferences, labels, error association, and tested interaction states. This removes repeated risk. It cannot guarantee the accessibility of product content, workflow, composition, data, or custom extension.

Guide: Teams need clear responsibility at both levels.

Guide: Documentation includes failure examples: icon-only status, colour-only urgency, live regions that announce every refresh, inaccessible interactive cards, and tables that lose header relationships on small screens. Escape hatches are reviewed and measured.

Guide: Defects in shared code receive severity and response appropriate to their distribution because one flaw can reach every product.

Transfer example: modal dialog

Host: What changes when we look at transfer example: modal dialog?

Guide: A library can supply focus containment and escape behaviour, but a product can still create an inaccessible flow by opening nested dialogs, using an unclear title, or requiring a decision without necessary context. Component quality and journey quality need separate tests.

Encode accessible defaults and obligations

Host: What changes when we look at encode accessible defaults and obligations?

Guide: Foundations protect contrast, typography, spacing, motion, and focus. Components encode semantics, names, roles, states, keyboard interaction, target size, announcements, error behaviour, zoom and responsive rules.

Guide: Documentation must also state what the consuming team supplies: meaningful labels, heading order, alternative text, focus destination, timing, and task-level testing.

Guide: Test in layers. Automate stable code rules, run unit and interaction tests, inspect semantics, use keyboard and assistive technology, validate themes and forced colours, zoom and reflow, and test components in representative compositions. Include disabled people in research on high-impact patterns.

Guide: Version accessibility changes carefully. Fixes can alter focus, DOM order, size, or content and require migration. Communicate impact and verify downstream products. Track exceptions and defects back to shared causes; a system should prevent recurrence rather than merely distribute patches.

Guide: Assign accessibility ownership but keep responsibility distributed. System teams provide a strong path; product teams remain accountable for journey, content, configuration, and third parties. Measure shipped task quality, not only library conformance.

Split responsibility without creating a gap

Host: What changes when we look at split responsibility without creating a gap?

Guide: Testing forms a pyramid: static analysis and automated checks on every change; contract and interaction tests for components; keyboard, screen reader, zoom, high contrast, and motion review; product-flow regression; and research with disabled people for real understanding and action. Shared defects receive severity proportional to their reach and a supported remediation path.

Guide: Escape hatches are visible and governed. Teams record why they override, who is affected, temporary mitigation, owner, and expiry. Trends feed the roadmap. Accessibility metrics include critical-path coverage, recurrence, old-version exposure, exception age, and customer impact—not only automated pass rate.

Transfer example: dialog systems

Host: What changes when we look at transfer example: dialog systems?

Guide: A component can manage focus and escape correctly, yet a product can open nested dialogs, omit necessary context, or demand an irreversible decision. The system raises the floor; journey design determines whether the experience is accessible.

The harder decision

Host: Where does the harder design decision appear?

Guide: The system should make the accessible path the easy path. If product teams must repeatedly add custom fixes, the system has not solved the shared problem.

Look more closely

Host: What should we look at more closely?

Guide: Make the accessible path the default path. System components should document semantics, keyboard operation, focus, target size, labels, announcements, contrast, motion, responsive behaviour, and known limits. Combine automated checks with manual interaction, assistive-technology testing, and evaluation of complete product journeys.

Guide: A component can meet isolated criteria while a flow fails at state change, composition, or recovery.

Guide: Failure modes to watch

Guide: Accessibility badge: a component is marked compliant without task or assistive-technology evaluation. API escape hatch: teams can easily remove semantics or focus behaviour to achieve a visual goal. Composition blind spot: accessible pieces form an inaccessible dialog, menu, or flow.

Guide: No remediation owner: known barriers persist because a system team and product team each assume the other will fix them.

Product example

Host: Can we see that in a concrete product situation?

Guide: A system’s button component has good contrast in its default state, but loses focus visibility, announces an unclear label, and cannot be reached by keyboard inside a modal. The system has spread the defect efficiently.

Connect the lessons

Host: How does this connect to what we have already learned?

Guide: M10 now connects the design system’s product purpose, foundations, change process, and access quality. M11 extends systems thinking beyond software into people, operations, policy, and service.

Try it yourself

Host: What should I notice the next time I use a product?

Guide: Choose one system component. List its states, input methods, accessible name, focus behaviour, error handling, and the context where it is most likely to fail.
