Foundations and Components

This recording is an editorial draft adapted from the revised lesson. It has not completed the final dialogue and audio review.

Before we begin

Host: Foundations and Components.

Guide: Foundations include shared decisions such as colour, type, spacing, elevation, motion, accessibility, and content principles. Components package recurring interface behaviour. Patterns describe how components work together for a task. A robust system documents purpose, variants, states, constraints, examples, and implementation guidance.

Why it happens

Host: Why does that happen?

Guide: Design tokens can make foundational decisions portable across platforms, but tokens do not replace judgement. Components should encode proven behaviour and make the accessible, consistent path easier than the ad hoc path.

From foundation to component contract

Host: What changes when we look at from foundation to component contract?

Guide: Foundations are the variables and rules that make a family of interfaces coherent: type scale, spacing, colour roles, elevation, motion, breakpoints, icon principles, and interaction states. Tokens give these decisions durable names. Components combine them into reusable behaviour. Patterns explain how components cooperate to solve a larger recurring problem.

Guide: Confusing these layers makes systems brittle: a token named blue-500 exposes appearance, while status-info-background records purpose and can change across themes without changing meaning.

Guide: A component contract states more than props. It includes purpose, when to use it, when not to, content limits, supported states, responsive behaviour, keyboard and screen-reader behaviour, error and loading conditions, data dependencies, analytics events, and examples with realistic language. The code, design asset, documentation, and tests must express the same contract.

Guide: If the design asset allows a state that the code cannot render, the system already contains drift.

Transfer example: destructive action

Host: What changes when we look at transfer example: destructive action?

Guide: A reusable delete dialog may look consistent yet be unsafe if every product supplies different consequences. A stronger contract distinguishes removal, revocation, cancellation, and permanent deletion; requires the affected object and consequence in the confirmation; defines undo or recovery expectations; and blocks generic success copy.

Guide: The component is reusable because its behaviour and meaning are stable, not because its rectangle is stable.

Build from decisions upward

Host: What changes when we look at build from decisions upward?

Guide: Foundations include colour, typography, spacing, elevation, motion, iconography, grids, language, accessibility, and interaction principles. Express recurring values as tokens with semantic names such as text-danger or surface-selected, not names tied to one current appearance.

Guide: A component is a behavioural contract, not a rectangle. Define anatomy, variants, states, content, keyboard and assistive-technology behaviour, responsive rules, error and loading, theming, and prohibited use. Compose components into patterns for meaningful tasks while keeping domain logic in products where appropriate.

Guide: Test foundations and components in combinations with real content, zoom, translation, themes, and edge states. Small token changes can affect the entire estate; system leverage magnifies both quality and mistakes. Version and communicate changes accordingly.

Specify behavior before variants multiply

Host: What changes when we look at specify behavior before variants multiply?

Guide: Each component contract covers anatomy, allowed content, states, interaction, keyboard and screen-reader behavior, responsive change, internationalisation, data conditions, and when not to use it. Variants represent meaningful product differences, not every local styling request.

Guide: A “clinic option” may compose comparison data, availability, selection, and warnings; it should not absorb unrelated promotional cards because their rectangles look similar.

The harder decision

Host: Where does the harder design decision appear?

Guide: Component APIs shape product behaviour. Decisions about variants, defaults, and escape hatches determine whether the system supports thoughtful design or forces misleading uniformity.

Look more closely

Host: What should we look at more closely?

Guide: Foundations express durable decisions at a lower level of abstraction: semantic colour roles, typography scale, spacing, grid, elevation, motion, focus, iconography, and content principles. Tokens give these decisions portable names so implementations can adapt without exposing raw values everywhere.

Guide: Components then combine structure, semantics, interaction, state, and content slots into a reusable behaviour. Patterns describe how components collaborate to support a task.

Guide: Document a component as a contract: purpose, when to use or avoid it, anatomy, variants, states, accessibility behaviour, content guidance, responsive behaviour, code API, and examples of real use. Test it under real content, loading, error, empty, permission, and localisation states.

Guide: Version changes carefully because a small token or component decision can affect many customer journeys.

Guide: Failure modes to watch

Guide: Token cargo cult: a large naming system is created without semantic meaning or governance. Happy-state component: documentation omits error, loading, disabled, and empty behaviour. Design-code drift: visual assets and implementation evolve separately. Variant explosion: every local exception becomes a permanent component option.

Product example

Host: Can we see that in a concrete product situation?

Guide: A “button” is not one thing. It has hierarchy, label rules, loading, disabled, focus, hover, error, success, mobile, keyboard, and assistive-technology behaviour. A component that names only its default state is unfinished.

Connect the lessons

Host: How does this connect to what we have already learned?

Guide: Worked example A date picker is not complete when it matches the visual library. It must support typing, calendar selection, localisation, min and max constraints, unavailable dates, errors, keyboard movement, announcements, zoom, and mobile input. If the domain needs ranges or uncertain dates, the system may need a pattern rather than another variant.

Guide: The component contract makes those decisions visible before dozens of products invent incompatible answers. Systems exist to scale quality. Foundations and components provide the building blocks. lesson 51 ensures content is treated as part of those blocks rather than pasted in afterwards.

Try it yourself

Host: What should I notice the next time I use a product?

Guide: List the states a button needs beyond default. Which states become important in a high-risk or slow operation?
