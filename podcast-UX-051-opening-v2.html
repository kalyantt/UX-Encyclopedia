Content in the System

This recording is an editorial draft adapted from the revised lesson. It has not completed the final dialogue and audio review.

Before we begin

Host: Content in the System.

Guide: Content standards belong in a design system because reusable components carry meaning as well as visual form. Define labels, voice, error structures, confirmation patterns, empty states, variable content rules, and localisation constraints. This makes clear language easier to apply consistently.

Why it happens

Host: Why does that happen?

Guide: Content design must remain contextual. A system can give principles and patterns, but it should not turn every message into a generic template. The component should expose the information a writer needs to express the real consequence and next action.

Content is part of the behavioural contract

Host: What changes when we look at content is part of the behavioural contract?

Guide: System content has three layers. Voice principles establish durable qualities such as direct, respectful, and calm. Content patterns describe how meaning changes across recurring situations—errors, confirmation, empty states, permission requests, progress, and destructive actions.

Guide: Component content rules specify the slots, constraints, and relationships required for one implementation. A slogan about tone cannot replace any of these layers.

Guide: The content API encodes meaning rather than accepting arbitrary strings. A referral-status component receives a governed state, timestamp source, responsible actor, next-action type, and optional explanation. The rendering layer selects tested language and exposes controlled extension points for legitimate clinical detail.

Guide: This reduces accidental contradiction across UI, email, SMS, and support. It also makes localisation and accessibility review possible before a product team invents a sentence under deadline pressure.

Transfer example: payment failure

Host: What changes when we look at transfer example: payment failure?

Guide: “Something went wrong” is visually reusable and operationally useless. A payment pattern needs to distinguish bank decline, expired method, network uncertainty, duplicate-risk state, and merchant rejection because each permits a different next action. The system should prevent a team from confidently saying “not charged” when the transaction state is unknown.

Guide: Content governance protects truth under uncertainty.

Treat language as system behaviour

Host: What changes when we look at treat language as system behaviour?

Guide: Define content principles, voice, terminology, grammar, action labels, error patterns, status, confirmation, and accessibility guidance alongside visual components. A button API without rules for naming the action still creates inconsistent decisions.

Guide: Design content slots around purpose and limits. Specify required labels, helper text, error association, dynamic values, localisation expansion, pluralisation, and screen-reader context. Avoid placeholder strings that make layouts look stable while real languages and data break them.

Guide: Govern shared terminology through a controlled vocabulary and ownership. When product domains need different words, document the audience and meaning rather than forcing superficial consistency. Test component content in the complete task: the same phrase can be clear in one state and ambiguous in another.

Systematise meaning without flattening context

Host: What changes when we look at systematise meaning without flattening context?

Guide: The system documents terminology, definitions, prohibited ambiguity, voice principles, localisation notes, and content accessibility. Content tokens are used carefully; a reusable string is appropriate only when meaning and grammar stay stable. Concatenating fragments can break translation and screen-reader comprehension.

Guide: Examples include realistic edge cases rather than polished success copy.

The harder decision

Host: Where does the harder design decision appear?

Guide: Content governance needs ownership and contribution paths. Otherwise teams fork labels and messages as quickly as they fork visual components.

Look more closely

Host: What should we look at more closely?

Guide: Content patterns should define the information a component needs, not only a string length. A confirmation may need action, object, status, time, consequence, and next step; an error may need problem, location, repair, and support route.

Guide: Document voice principles, label grammar, punctuation, capitalisation, variable rules, truncation, translation, and accessible names so content is treated as behaviour rather than decoration.

Guide: Create components with meaningful slots and constraints. “Title” and “body” may be too generic when a message needs an outcome or next action. Work with writers and localisation specialists early; a concise English label may become much longer or grammatically different elsewhere.

Guide: Allow contextual authoring where meaning changes, while ensuring the base pattern prevents known ambiguity and inaccessible defaults.

Guide: Failure modes to watch

Guide: Lorem-ipsum system: components are designed without realistic content or states. Template voice: reusable wording erases the actual consequence or task. Truncation as solution: important information is clipped rather than structurally supported. Unowned copy: no one maintains terminology, examples, or translation guidance.

Product example

Host: Can we see that in a concrete product situation?

Guide: One confirmation says “Done,” another says “Success,” and a third says “Your request is being processed.” The words are not decoration; they change whether people understand the state.

Connect the lessons

Host: How does this connect to what we have already learned?

Guide: Worked example For a destructive action, the system defines title, consequence, primary action named with the real verb, cancel path, and recovery information. Products supply the object and irreversible effect; they cannot replace it with “Continue.” Translation tests reveal whether the component accommodates longer action labels.

Guide: Screen-reader review checks that context is not carried only by the surrounding visual layout. Content rules have become executable quality rather than a page in a style guide. Components make interaction repeatable; content makes that interaction understandable. lesson 52 begins the practical work of introducing a system through a focused pilot.

Try it yourself

Host: What should I notice the next time I use a product?

Guide: Compare confirmation labels across a product. Are they systematically clear about outcome, state, and next action?
