Use Interaction Patterns Without Cargo Culting

This recording is an editorial draft adapted from the revised lesson. It has not completed the final dialogue and audio review.

Before we begin

Host: Use Interaction Patterns Without Cargo Culting.

Guide: An interaction pattern is a reusable response to a recurring problem in a particular context. It captures forces, trade-offs, and a structure that has worked before. A pattern is not a visual trend or a component to paste into every screen.

Why it happens

Host: Why does that happen?

Guide: Start with the user goal, context, content, frequency, consequence, and constraints. Then ask what problem the pattern solves, what it assumes, and what it makes harder. Adapt or reject it when those assumptions do not hold. Test the behaviour in the actual task rather than treating convention as proof.

Transfer example: audit history

Guide: Infinite scroll supports casual discovery but undermines stable reference, total scope, and return position in an audit log. Pagination with persistent filters is less fashionable and more appropriate because the work demands defensible retrieval.

Evaluate the pattern’s contract

Host: What changes when we look at evaluate the pattern’s contract?

Guide: Name the problem the pattern solves, assumptions it makes, expected mental model, states, accessibility behaviour, content, data, and failure. Compare those with the current context. A familiar pattern reduces learning only when it preserves familiar meaning; copying its shape while changing behaviour creates negative transfer.

Guide: Research how people currently solve the task and inspect platform conventions. Prototype realistic edge states and alternatives. Check whether the pattern fits frequency, expertise, consequence, device, and information complexity. Adapt deliberately and document the reason so later teams do not “correct” an intentional difference.

Guide: Measure task success, error, recovery, comprehension, and long-term efficiency—not novelty or stakeholder familiarity. Contribute repeated validated adaptations back to the system. Patterns are accumulated hypotheses, not universal laws.

Evaluate the forces the pattern balances

Host: What changes when we look at evaluate the forces the pattern balances?

Guide: The pattern contract states problem, context, assumptions, anatomy, behaviour, states, accessibility, content and data requirements, failure modes, analytics, and exception criteria. Tests include realistic extremes: many options, missing values, long translation, stale state, keyboard and screen reader, narrow width, interruption, and simultaneous availability change.

Guide: Adaptation has a decision record. Later teams can see why the library pattern changed and what evidence would justify convergence or further variation. Repeated validated exceptions can become a new shared pattern; one stakeholder preference does not. A design system that enforces appearance without preserving task fit converts reuse into cargo culting.

Transfer example: activity history

Guide: Infinite scroll suits casual feed discovery but undermines total scope, stable return, export, and defensible reference in an audit log. Pagination and persistent filters may feel less modern while satisfying the actual forces.

The harder decision

Host: Where does the harder design decision appear?

Guide: Pattern libraries should document when not to use a pattern. The exception criteria are often more valuable than the screenshot.

Look more closely

Host: What should we look at more closely?

Guide: Assess patterns against the whole task: information density, user expertise, input method, frequency, error cost, access needs, device, collaboration, and service constraints. A familiar pattern may reduce learning cost while still harming comparison, speed, or recovery.

Guide: Document rationale and exception criteria so a pattern library teaches judgment rather than enforcing visual imitation.

Guide: Failure modes to watch

Guide: Trend transfer: a consumer pattern is copied into a high-density or high-risk workflow. Component-as-solution: a reusable UI element is selected before the underlying task is understood. Convention claim: familiarity is used as proof without testing task fit. No exception path: teams cannot adapt a pattern when its assumptions fail.

Product example

Host: Can we see that in a concrete product situation?

Guide: A team copies a popular card layout into an enterprise workflow. It looks familiar, but hides comparison details, slows keyboard users, and makes bulk action difficult. Familiarity was mistaken for fit.
